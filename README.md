# MIXORA catalogue backend

This standalone Next.js and TypeScript service stores catalogue metadata in Cloudflare D1 and private audio objects in Cloudflare R2. D1 is the relational database; R2 holds audio bytes. The Android project remains separate. No licensed recordings or provider feed are configured.

## Configure Cloudflare

Create a D1 database and a private R2 bucket in the same Cloudflare account. Create a scoped API token with D1 read/write access and an R2 S3 API token scoped to the bucket. Copy `.env.example` to `.env.local` and fill in the account ID, D1 database ID, API token, R2 bucket name, R2 access key ID and R2 secret key. Keep `.env.local` private. `R2_ENDPOINT` is optional; the backend constructs it from the account ID.

For a fresh database, run `pnpm install`, `pnpm db:migrate`, and `pnpm demo:generate`. Review migration history before running migrations against an existing production database. Use `pnpm cloud:verify` to compare the remote D1 table, columns and indexes with `schema.sql`, and to upload, retrieve, verify and remove a temporary original WAV in R2. Then run `pnpm catalog:verify-demo` to import the WAV, confirm the stored D1 metadata and R2 bytes, check duplicate handling and prove that the development track remains unpublished. Start the API with `pnpm dev`. `GET /api/catalog` returns the existing `schemaVersion: 1` snapshot with no tracks until an eligible track is published.

For inbox imports, place MP3 or PCM WAV files in `data/imports/` and run `pnpm catalog:import`. The optional `<audio-file>.json` sidecar sets title, artist, album, year, genre, category, language, BPM, key, energy and rights fields. Inbox files are preserved. Unchanged files and matching checksums are skipped. Imports go into R2 and D1 but remain unpublished.

For artist or provider submissions, use `pnpm catalog:import-manifest path/to/manifest.json`. The manifest and source audio stay local to the import machine. `pnpm catalog:publish <track-uuid>` requires documented rights holder, evidence reference, rights basis, and explicit distribution, offline and mixing permissions. Development audio cannot be published. The public catalogue repeats those checks; the media route currently denies all audio requests. A future licensed feed can use `PROVIDER_FEED_URL` and `PROVIDER_FEED_TOKEN`; leave both empty until a real agreement exists.

The music R2 bucket is accessed by the backend through its binding or separate S3 credentials. `/api/media/[id]` currently returns the same generic denial for every public request without reading D1 or R2; the public catalogue remains metadata-only even though its v1 `audioUrl` field is preserved. Verify the bucket has neither public `r2.dev` access nor a public custom domain before deployment. Listener authentication, streaming and offline entitlements, and an approved offline licence flow are mandatory before commercial listener launch. Never use YouTube scraping or unauthorised recordings.

## Production catalogue preparation

The additive `0002_partner_review` D1 migration records independent artists, distributors and labels as partners, and records append-only track rights reviews. Imports remain unpublished. Publishing now requires a verified partner and an approved review tied to the current import fingerprint, audio SHA-256 and private rights reference. D1 triggers block direct publication without that review. For a new environment, review and apply the migration history before deployment. The existing production D1 has migrations through 0006; verify their status read-only before any new migration. Run `pnpm cloud:verify` only when a write-capable verification is explicitly approved. No real partners or rights are created by the migration.

The trusted operator commands and their limits are in [docs/review-workflow.md](docs/review-workflow.md). The Android full-snapshot contract is in [docs/android-catalog-api.md](docs/android-catalog-api.md). The current metadata fields cover title, artist, album, year, category, genre, language, duration, BPM, key, energy, audio format, size, checksum, source and rights. The additive `0003_staff_roles` migration provides Cloudflare Access JWT verification and D1 role grants for staff CLI actions. The existing `mixora-team` Cloudflare Access application and `mixora-staff-login` Worker provide a staff sign-in entry point. The team domain and separate backend-app AUD are configured locally; a fresh backend-app JWT is still needed to confirm the live Access audience; staff commands still require a verified human JWT and an explicit role grant. An unauthenticated request to the Worker redirects to Cloudflare Access. A user reports a successful browser sign-in and one short-lived PARTNER_REGISTRAR grant is present in D1; live read-only CLI JWT authorization passed on 18 November 2026. No roles are seeded automatically. Stage 2 adds append-only, HMAC-chained review events with explicit approval, rejection and revocation reasons, staff actor IDs, exact metadata/audio/evidence hashes, and self-review guards. See [docs/review-workflow.md](docs/review-workflow.md) and run `pnpm audit:verify` after migration. Album artwork ingestion, extra release identifiers, listener authentication and entitlement checks remain future work; do not describe this preparation as a commercially ready service.

The old PostgreSQL metadata snapshot is preserved under ignored `data/migration/postgres-catalog.json`; the previous PostgreSQL server and its data were not deleted. Existing rows were unpublished test records, and their local audio was absent when the snapshot was taken. They are not automatically promoted or copied to D1. Provision D1/R2 and run live verification before connecting Android.

Stage 3 adds private agreement PDFs in a separate R2 bucket, immutable D1 agreement metadata and HMAC-audited staff-only upload, inspection, retrieval and decisions. Publication now requires a current verified private agreement. Configure separate bucket credentials and apply `0005_protected_agreements` before use; see [docs/protected-agreements.md](docs/protected-agreements.md). The private legal-agreement bucket has separate bucket-scoped credentials in the gitignored local environment, and a prior synthetic upload/retrieval/delete check passed. No actual agreements have been verified; see `docs/protected-agreements.md`.
